## Fixed on this branch

1. **Approvals and holdings outside SOL/USDC were not checked before signing** (`src/micro/guard.ts`). The pre-sign simulation compared only the SOL balance and the USDC balance. A modified Jupiter response could add an SPL `Approve` or `SetAuthority` on the USDC account (balances unchanged in simulation) or move another token in the wallet, and with Auto-Confirm enabled nobody would review it. The guard now rejects a simulated USDC account with a delegate or close authority (`SIMULATED_TOKEN_AUTHORITY`) and requires every other non-empty token account of the wallet to be byte-identical before and after the simulation (`UNSCOPED_HOLDING_CHANGED`). Two regression tests; both fail on the original code.
2. **A crash left the instance lock behind** (`src/utils/fs.ts`, `dashboard/server/trading.ts`, `src/micro/runtime.ts`). Closing the console window or a crash skipped cleanup, and every later connect failed with `INSTANCE_LOCK` until `data-micro/micro-LIVE.lock` was deleted by hand. The lock is now replaced only when the PID recorded in it no longer exists; a live, foreign-user or unreadable owner still blocks. This is safe because an unresolved transaction is held by the ledger's `pending` entry, which halts trading on the next scan, not by the lock. Regression test included; it fails on the original code.
3. **`npm ci` failed for the dashboard on npm 10** (`dashboard/package-lock.json`). The lockfile written by npm 11 on Raven lacked `jayson`'s optional peer `utf-8-validate@5.0.10`; npm 10 (bundled with Node 22 LTS, the likely VPS runtime) refused to install. Regenerated with npm; `npm ci` now passes on npm 10 and npm 11.

4. **Every live scan failed with `USD_PRICE_MISSING`** (`src/micro/market.ts`, `src/data/wallet-monitor.ts`), found during the first real connect on Raven. DexScreener lists USDC only as the base of a USDC/USDT pool, and pair selection accepted only SOL or USDC quotes, so USDC never received a price: the micro session could not pass its first gate, and the wallet panel showed a partial USD valuation. Valuation of held assets now also accepts USDT-quoted pools; strategy discovery keeps its SOL/USDC-only quotes. The wallet test fixture had priced USDC through a USDC/SOL pool that the real API does not return; it now mirrors the actual response.

The three new rejection codes have explanations in the trading panel.

## Open before real money

- **Phantom may alter the transaction it signs.** Phantom can add Lighthouse assertion instructions to transactions it signs. The browser and the server both, deliberately, reject any change to the message (`Transaction changed during signing` / `SIGNED_MESSAGE_CHANGED`). If Phantom alters these swaps, every trade stops at signing: a safe failure, but the live path would not work. Only a real connect + manual approval on Raven can show this; do it once with Auto-Confirm off before funding.
- **The end-to-end Phantom flow is still unverified.** Automated browsers cannot load the extension. The UI and API were verified; connect, sign and Auto-Confirm were not.
- **Dependency findings** (`bigint-buffer` via `@solana/spl-token`, `uuid` / `stream-json` via `@solana/web3.js`) have no upstream fix. The call-path assessment in `TRADE-READINESS-2026-09-29.md` stands; it still needs a formal decision before the VPS rollout.
- **Wrapped SOL in the micro wallet blocks trading.** Jupiter wraps and unwraps through the wallet's wSOL account and closes it after the swap; a pre-existing wSOL balance therefore fails the new unchanged-check (`UNSCOPED_HOLDING_CHANGED`). Unwrap it in Phantom first. This is a deliberate safe failure: before the fix, that balance would have been unwrapped silently into the trade's SOL accounting.
- **Other token accounts with a zero balance** are not included in the new unchanged-check (no value at risk now). Keep the micro wallet dedicated, as the panel already recommends.
